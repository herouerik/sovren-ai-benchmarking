# Handover from the M4 session, 2026-08-21

Written for the GPU-server Claude session. Everything below is pushed to
`main`. Read this before re-planning — three of today's findings change what
is safe to run and what the existing numbers mean.

## 1. A harness bug was silently zeroing both EvalPlus columns

`harness/sandbox.py` ran generated code with bare `"python3"`, which resolves
through PATH and so only finds the venv when the venv is *activated*. Run as
`.venv/bin/python run_benchmark.py` it hit the system interpreter, which has no
numpy — and EvalPlus test suites import numpy. Result: 97 of 100
`humaneval_plus` samples failed with `ModuleNotFoundError` while the model's
code was correct, scoring `qwen3.6:35b-mlx` **0.00 on a benchmark where it
actually gets 0.87**.

Fixed in `f7e66de` to `sys.executable`. **This affects the GPU server too**:
if that box has been running without an activated venv, any
`humaneval_plus`/`mbpp_plus` cell it produced is suspect. The signature is a
0.00 on both EvalPlus columns for a model that scores normally on plain
`humaneval`/`mbpp`. Worth grepping your own raw results for
`ModuleNotFoundError` before trusting those columns.

## 2. Two committed rows carry false zeros — decision needed

`nemotron-cascade-2:latest` and `qwen2.5-coder:32b` both show
`bfcl_irrelevance=0.00, humaneval_plus=0.00, mbpp_plus=0.00` with
`speed: 0.0`. **Both models no longer exist in Ollama on the M4** —
`/api/show` returns MISSING. So the remote run could not reach them and every
request failed to 0.00.

This is not the numpy bug (other models in the same batch scored 0.79-0.91 on
he+). It is the same artefact class as the `deepseek-r1: bfcl 0.0 -> None`
correction already made in `7db02af`/`ca76f04`, and those cells should become
`None` for the same reason. **Not changed yet — needs a call on whether to
correct the published numbers or re-pull the models and measure them.**

Note a 0.00 on `bfcl_irrelevance` reads as "calls a tool every time", which is
a plausible-looking score rather than an obvious failure. It is the most
misleading of the three.

## 3. M4 rows should be driven FROM the M4, not remotely

Inference happens on the M4 either way, so driving remotely buys no speed. It
costs two things:

- `pressure.py::_is_local()` compares base_url against the driving machine's
  LAN IP. Remote, the memory guard falls back to timing-only detection instead
  of reading the M4's real `vm_stat` swap counters — which is what caught a
  thrash event today.
- The EvalPlus sandbox executes on the *driving* host, not the one under test.

Remote is for when the laptop cannot be sat in front of. `config-m4-remote.yaml`
now says this at the top, and its IP is refreshed to **192.168.68.109**
(fourth address this week — re-verify before every remote run).

## 5. What contention cost, and what it did not

An unnoticed opencode session held `qwen3.8:27b-mlx` resident (~17-22GB) all
morning. Every eviction attempt was answered by a fresh runner with
`expires_at` pushed out 5 minutes; `evict_all()` cannot override another live
client, and that limit is now documented in `harness/client.py`.

Audited: it did **not** contaminate the committed numbers. needle2 is CPU-only
and untouched; `qwen3.8:27b-mlx` irrelevance (68/100) had zero errors because
it benchmarked the already-resident model rather than loading a second one;
`qwen3.6:27b-mlx` (86/100) was clean. The one casualty is a single sample in
`qwen3.6:27b`, being re-measured by `config-m4-recheck.yaml`.

## 6. Speed numbers: a caveat I raised and then withdrew

`speeds[model]` now also has `speeds_by_benchmark` and `speed_basis`
(`e9d50e5`). Read the commit message before drawing conclusions: I chased a
suspected 44% benchmark-mix bias in the speed column and it was **not real** —
those medians came from the end-to-end `tok_per_sec` field, which includes
prefill. The aggregator reads `decode_tps`, which excludes it, and the same
data shows 0.4% spread. The change is observability, not a correction.

The genuine trap: `tok_per_sec` and `decode_tps` diverge sharply on
short-output benchmarks. Do not mix them.
