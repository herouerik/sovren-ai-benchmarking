## 1. A harness bug was silently zeroing both EvalPlus columns

`harness/sandbox.py` ran generated code with bare `"python3"`, which resolves
through PATH and so only finds the venv when the venv is *activated*. Run as
`.venv/bin/python run_benchmark.py` it hit the system interpreter, which has no
numpy — and EvalPlus test suites import numpy. Result: 97 of 100
`humaneval_plus` samples failed with `ModuleNotFoundError` while the model's
code was correct, scoring `qwen3.6:35b-mlx` **0.00 on a benchmark where it
actually gets 0.87**.

Fixed in `f7e66de` to `sys.executable`. **This affects the GPU server too**:
if that box has been running without an activated venv, any
`humaneval_plus`/`mbpp_plus` cell it produced is suspect. The signature is a
0.00 on both EvalPlus columns for a model that scores normally on plain
`humaneval`/`mbpp`. Worth grepping your own raw results for
`ModuleNotFoundError` before trusting those columns.

> **RESOLVED (`c446039`).** The GPU server checked: zero `ModuleNotFoundError`
> hits across all its raw result files, and no 0.00-on-plus-with-normal-plain
> pattern in any GPU-server row. Its EvalPlus data was never affected — it runs

## 3. M4 rows should be driven FROM the M4, not remotely

Inference happens on the M4 either way, so driving remotely buys no speed. It
costs two things:

- `pressure.py::_is_local()` compares base_url against the driving machine's
  LAN IP. Remote, the memory guard falls back to timing-only detection instead
  of reading the M4's real `vm_stat` swap counters — which is what caught a
  thrash event today.
- The EvalPlus sandbox executes on the *driving* host, not the one under test.

Remote is for when the laptop cannot be sat in front of. `config-m4-remote.yaml`
now says this at the top, and its IP is refreshed to **192.168.68.109**
(fourth address this week — re-verify before every remote run).

short-output benchmarks. Do not mix them.

## 8. Running two sessions in parallel, and merging afterwards

Two Claude sessions now work this repo at once: one on the MacBook M4, one on
the i9 GPU server. This is the protocol that keeps that safe. It is written as
rules rather than suggestions because every one of them corresponds to a way we
already lost data or time this week.

### Rule 1 — a session only drives its own hardware

| session | owns | endpoints |
|---|---|---|
| M4 | MacBook M4 models | `localhost:11434` |
| GPU server | P100 array, RTX 2080 Ti (GPU0) | `192.168.68.115:11434`, `:11437` |

Never point a config at the other machine's Ollama while that machine is also
running its own harness. Two harnesses on one Ollama will co-resident two large
models: on a 48GB laptop that is instant swap, measured at **0.2 tok/s with
request timeouts** for a model that does 72 tok/s alone. A whole morning's
attempts were lost to a variant of this (an editor session, not a harness, but
the same mechanism — see §5).

`config-m4-remote.yaml` exists for when the laptop cannot be sat in front of.
It is not the default, and §3 explains what it costs.

### Rule 2 — commit per-run aggregates, never hand-merge the derived files

`.gitignore` already encodes this split:

- `results/*.summary.json` — **tracked**. One per run, written by
  `scoring/generate_report.py --summary`. These are the source of truth and
  each belongs to exactly one session. Give them distinct names
  (`m4_fill_*`, `rtx2080_*`, `gpu_fill_*`) so two sessions never write the
  same path.
- `results/<timestamp>.json` — untracked. Multi-MB per-sample records, local
  to the machine that produced them.
- `results/merged.summary.json` and `results/report_final.html` — **derived**.
  Rebuilt from the aggregates by `merge_summaries.py`. Both sessions regenerate
  them on every run, so they will conflict constantly.

**Never resolve a conflict in a derived file by choosing a side.** Taking one
version wholesale silently drops the other machine's rows, and because the file
still looks complete and well-formed nothing catches it. Regenerate instead.

### Rule 3 — the merge sequence

Whoever finishes a batch does this, in order:

```sh
# 1. land your own aggregate only
python scoring/generate_report.py results/<run>.json --summary results/<name>.summary.json
git add results/<name>.summary.json && git commit
# 2. take the other machine's work first
git stash push -- results/merged.summary.json results/report_final.html   # if dirty
git fetch origin && git rebase origin/main        # rebase, not merge: keep history linear
# 3. rebuild the derived files from EVERY aggregate now present
python merge_summaries.py results/merged.summary.json results/<name>.summary.json \
    --summary results/merged.summary.json --output results/report_final.html
# 4. verify nothing pre-existing moved, then push
git add results/merged.summary.json results/report_final.html && git commit && git push
```

Step 3 is deterministic, so it is always safe to redo. If a rebase conflicts on
a derived file, `git checkout --theirs` it, then rerun step 3 — the content is
reproducible from the aggregates.

### Rule 4 — verify the merge did not eat anything

`merge_summaries.py` is last-file-wins per `(model, benchmark)` cell, so a
stale aggregate can overwrite a newer score. Check before pushing:

```python
old = json.load(open('<merged before>')); new = json.load(open('<merged after>'))
changed = [(m,b,v,new['scores'].get(m,{}).get(b))
           for m,bs in old['scores'].items() for b,v in bs.items()
           if new['scores'].get(m,{}).get(b) != v]
```

Expect `[]`, or only cells you deliberately re-measured. This check has already
caught real problems twice: it is how the stale `total_samples: 10970` (against
a real 8,370) was found, and it is what confirms a `0.0 -> None` correction is
the only thing a commit changed.

### Rule 5 — host labels must be explicit

`execution.host_label` is required in every config whose `base_url` is
`localhost`, otherwise `_infer_host_label()` returns a generic same-machine
string and those rows will not merge alongside the same host's other rows.
This has cost two recoveries already (`7db02af`, `b7a1721`).

### Rule 6 — pass findings through docs, not through inference

Neither session sees the other's terminal. Anything the other session needs in
order to plan differently goes in a `docs/HANDOVER-*.md` or a commit message,
in the same push as the code it describes. A harness fix pushed without its
explanation gets pulled and then not acted on — the `sys.executable` fix in §1
is only useful to the server session because §1 tells it what to grep for.

### What is genuinely parallel, and what is not

Parallel: inference, scoring, per-run aggregates. Each session can run for
hours without coordinating.

Not parallel: the derived files, and any decision that edits already-published
numbers (like the false zeros in §2). Those need one owner at a time.
